# Robot models and resources

Use this guide when selecting a robot, integrating a new model, or reviewing its provenance. The candidates are leads for finding resources. You may also select commonly used real models outside this list. Every production robot needs a verifiable model identity and source. Do not invent a rail, link, or joint mechanism for the task or change degrees of freedom, link lengths, or kinematics to achieve success. This applies to configurations, direct `world.stage` construction, and generated assets.

You may select an existing manufacturer or benchmark combination. Identify the exact base, arms, grippers, and version. Multiple instances of real arms may work together if each retains its original mechanism. The generator authors integration configuration, control, and tasks. Do not use a simplified substitute to cover a configuration gap. Document simulation approximations in official models and distinguish them from hardware capabilities.

## Selection and use

Honor the user's model choice. Otherwise, select by reach, payload, gripper, task, and available model. Match single-arm, dual-arm, mobile manipulation, and humanoid tasks to actual control capabilities. Choose for the task each time.

Keep model, joint, and controller provenance consistent. Distinguish Panda, FR3, UR5e, UR10e, and the different manufacturers' G1 models. Preserve mechanisms and metric dimensions. Allowed integration changes include resource path repair, name and coordinate mappings, supported material conversion, and official imports. Record original and derived digests, conversion scope, and unknown physical differences. Disclose a fixed base or partial joint control and use them only when appropriate. A fixed humanoid base cannot establish walking or balance. State teleportation, assisted grasping, and attachments in external examples do not establish real robot actions.

The following sources were checked on 2026-10-21. Models, action conventions, and policies do not automatically transfer across simulators. Check the selected version, license, and complete dependencies before downloading, and inspect the actual model before use.

## Local resources and external acquisition

Check the current host's prepared assets and pinned SDK prefix first. Verify local presence, preparation eligibility, and actual I/O through the current project_inspect, model, and frozen report. Do not maintain a second readiness registry or infer current task success from a historical loading, drive, or policy test.

For hosts with resources prepared on 2026-10-23, see `assets/robots/public-20261023/resource-inventory.json` under the configured data root for locations, original entries, versions, and known gaps. It records downloads and static dependency checks only. Prefer reusing the originals, keep caches read-only, and put derived files under the current project's imports. The LIBERO/PandaOmron source MJCFs are not directly loadable URDF/USD files. The presence of SDK material modules does not establish successful rendering or execution.

Check the licenses for BEHAVIOR's standalone unencrypted `omnigibson-robot-assets` and encrypted scene objects separately. The [official robot package declares MIT](https://huggingface.co/datasets/behavior-1k/omnigibson-robot-assets). Do not apply the terms for encrypted scene objects to all robot resources.

When the local host lacks a suitable model, use native search and terminal tools to obtain the complete official manufacturer or benchmark package. Pin its release or commit and exact configuration. Use a fresh directory under the configured data root's `assets/imports/<projectId>/` or `assets/imports/robots/<projectId>/`. Preserve relative layout and leave existing libraries read-only. Obtain actual Git LFS meshes, textures, collision files, and URDF package references. If inputs span multiple roots, assemble the complete closure in a new dedicated directory before freezing. Do not widen access to arbitrary host paths.

Prepare the complete closure through the [native file package interface](api.md#assets-and-materials). Use the report's name/sourcePage/license and pass the report reference to scene_build. Self-reported metadata cannot authenticate a model, establish a license, or prove success. The generator and independent reviewer verify provenance and structure.

`assets_prepare(url=...)` accepts self-contained HTTPS GLB files only. Obtain URDF, USD, and ZIP robot packages separately. A GLB's visual geometry does not supply real joints or drives. `world.robot` directly loads USD/USDA/USDC and URDF. MJCF/XML, xacro, archives, and model webpages are not direct entries. Prefer official USD/URDF for the same model. If an existing supported official converter is necessary, retain the original inputs, dependencies, conversion source, and recorded differences. Verify structure and actual I/O against [Robot configuration](api.md#robot-configuration). Changing an extension does not convert a model.

For a new model, author a public `*.robot.json` and reuse the same loading, planning, execution, and recording interfaces. See [Robot configuration](api.md#robot-configuration). Report loading, short drive segments, planning, grasping, cooperation, walking, and complete task success separately. Develop the policy further, find a matching algorithm, or report the gap. Use the [system wait interface](api.md#waiting-for-system-support) only for a verified blocker outside the project. Ordinary policy failure stays with the generator.

The system verifies resources and actual I/O. The generator's internal review decides whether the robot meets selection requirements. No additional host approval by model or brand is required.
