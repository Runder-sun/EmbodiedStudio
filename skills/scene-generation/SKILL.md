# Scene generation

Use the native Codex session to write project files, plan layouts, inspect images, and make repairs. Studio preserves the user's request, durable jobs, and execution receipts. The workbench host holds the editable project and system code. The simulation host holds assets, built revisions, and simulation data.

You and your subagents may write the current project's sources and necessary helpers, its `delivery/` directory, the configured data root's `projects/<projectId>/delivery/`, and new dedicated directories under `assets/imports/<projectId>/` or `assets/imports/robots/<projectId>/`. Treat existing raw records, frozen revisions, libraries, format-tool environments, other projects, the legacy repository, and Studio's src, runtime, tests, skills, configuration, host state, and services as read-only. Freeze external resources through the asset tools. Never run scripts bundled with downloaded models. Report blockers outside the project through the [system wait interface](references/api.md#waiting-for-system-support). Do not edit system files, request elevated privileges to change Studio, or restart its services.

Start with `project_inspect`. Read the complete saved request, requirement version, capabilities, absolute project path, and outstanding items. When writing or changing a program, read the relevant [API reference](references/api.md) and, if necessary, the indicated frozen runtime source. New projects start as skeletons. Write the scene, scoring program, and any behavior the request requires. World defaults to native construction with no robot. Older packages use their own frozen worker.

## Delivery scope

When `project_inspect.videoOnly=true`, deliver complete robot execution videos and their source mappings. Explicitly selected `environmentRefs` are read-only. If the user did not select an existing environment, prepare, build, and freeze the scene, tasks, and robot needed for recording in this project. Preserve the original task and follow the video-only contract in [Delivery](references/delivery.md). This mode does not require construction-history or environment training exports. Real execution, scoring evidence, and independent internal review still apply.

Read `requiredOutputs` from `project_inspect`. With `[generation,evaluation]`, deliver construction history and the evaluation environment. Leave robot selection, preparation, loading, expert behavior, and independent behavior collection to the later trajectory stage. With `[demonstrations]`, collect independently on the selected `environmentRefs`. The default requests all three products. Track outstanding items only for requested outputs and retain the construction history. Subsequent collection on a completed scene starts a new generation in the same project and preserves the original package, receipts, and failed attempts.

During the scene stage, write the scene, tasks, rubrics, and applicable verification sources. Environment delivery does not depend on successful robot execution or expert demonstrations. You and the independent reviewer choose verification of furniture joints, passive physics, scoring cases, and interfaces according to the task risk. Frozen cases may call `env.step` with an empty action. Prepare movable objects, joints, cavities, collisions, and materials that later execution needs. Pass an explicit `environmentSourceRefs=[...]` to `scene_build` covering `scene.py/tasks.py`, environment helpers, rubrics, and the case dependency closure. Add robot configuration only when needed. The isolated build cannot read unlisted files. For collection, keep the environment read-only and freeze independent behavior with `robot_run(behavior={sourceRef,helperRefs},repetitions=...)`. Behavior and export changes do not require an environment rebuild. Changing scene, task, or scoring does. If a frozen environment has no robot but supports `capabilities.robotSetup`, supply a real robot configuration, resources, installation pose, and independent behavior to `robot_run` through `robotSetup`. Reuse the returned `robotSetupRef`. Installation and behavior freeze independently. Add recording views appropriate to the robot and preserve the original cameras and policy permissions. See [Independent stages and layout sets](references/api.md#independent-stages-and-layout-sets). Report compatibility gaps in older packages. A collection-only job cannot rebuild the environment or edit its manifest.

Define legal layout sampling ranges and constraints in the scene source. Freeze different revisions of the same source using different `scene_build(seed=...)` values, reuse assets, and verify that the actual arrangement changes. Each revision resets to its own frozen initial state. Repetitions count episodes, not layouts. Use `environmentRefs=[{revision,split?,taskIds?}]` to record selected layouts and groups. Assign each revision to at most one split. Split training, validation, and final test layouts before collection. Keep episodes, camera views, rerenders, and repair derivatives of the same layout together. Run the student policy independently on test layouts. Never feed test outcomes back into training data or scoring. Report layout generalization separately from generalization to a new task or scene family. Studio does not prescribe a layout count or split ratio.

If the request includes robot demonstrations, read [Demonstrations and experience reuse](references/demonstrations.md) before starting or resuming collection. Develop a reusable expert from the existing project and actual records, then collect the requested layouts.

## Explicit raw-video mode

The user's latest instruction takes precedence over historical requests. When `project_inspect.recordOnlyVideos=true`, the request must also have `videoOnly=true` and `requiredOutputs=["demonstrations"]`. Execute the locked `recordOnlyTaskIds`. For each task, retain one actual successful video showing the robot starting in the original initial state and completing the entire original task. Reuse an existing successful episode when available. Report only the original video reference, taskId, revision, and episodeId. In this explicit mode, skip video review and delivery checks, do not summon `scene_quality_review`, author producer exports or producedArtifacts, call `project_deliver`, or export training data. Preserve the scene, physics, real robot control, completion conditions, sources, executions, failures, and interruptions. This exception overrides the general review, export, and delivery instructions below and in the references only for this mode.

## Construction and repair

- Declare the overall scope, purpose, and ownership tree. Expand each node into spaces, assets, supports, and tasks. Use one World for tabletop, room, multi-room, or building scope. Do not create a separate agent or planning tree per node. A node's `owner` defines membership and its `frame` defines its coordinate reference. Record support, containment, and connections separately. Keep stable IDs across repairs. Give fixed walls, slabs, ceilings, and roofs separate static objects with `role='enclosure'` so cutaway tools can disclose hidden geometry. Keep furniture, robots, task objects, and moving mechanisms out of this role. Preserve architecture and collisions during observation.
- In a multi-room scene, plan each room for its ordinary use as well as the user's task. Consider the activity areas, walls, and surfaces visible from its entrance. Reserve space for travel, manipulation, moving doors, and explicitly empty destinations. Decide how to use the remaining area, including where grouped furnishings or open space suit the room.
- By default, deliver a complete, well-finished scene appropriate to its scale and use. Both task objects and visible background furniture need complete shapes, plausible dimensions, materials, and support. Honor requests for simplified, schematic, or other styles. Recognizability or lack of interference with the task does not qualify a furniture blockout as final. Judge each visible piece as a whole regardless of its background or decorative label or number of parts. Reuse selected assets for repeated instances under the same conditions. Select alternatives for different requested styles or interactions. Architectural elements, collision proxies, and visibly simple objects can use primitives where appropriate. Evaluate the visible result independently of its construction and collision approximation.
- Select assets in order from preferred simulation libraries, the broad local library, online existing assets, and finally custom generation. A cache hit does not add a tier before preferred libraries. Start ordinary searches with `assets_lookup(libraryTier='preferred')`. For movable joints, check `collection='artvip'` first, then actual articulated candidates in other preferred collections. Record candidate fit, actual observations, or integration barriers that justify moving to another source or authoring an asset. Finding a candidate, freezing a file, or having a blockout does not finish selection. Apply the same quality standard to custom assets. Prioritize category, purpose, complete geometry, size, and necessary interactions. See [Assets and materials](references/api.md#assets-and-materials) for filters and unknown states.
- Compare actual candidate images, proportions, material detail, and style as needed. Reuse previews of the same item. Consider the whole room's materials, colors, and detail distribution. Inspect texture scale on floors, walls, windows, and other prominent surfaces at metric scale. A `publisher_render` is the publisher's preview. Preserve unknown dimensions, materials, and joints as unknown. You and the independent reviewer select, inspect, correct, and recheck the work. Missing resources do not relax the request. A primitive blockout or promotional image does not establish final quality.
- For robot data, select a real commonly used model or an existing public benchmark configuration appropriate to the original request. The [robot source guide](references/robots.md) lists leads. Do not invent mechanisms, add degrees of freedom, shorten links, or change kinematics for a task, including through configuration, `world.stage`, or generated assets. Integrate through public `*.robot.json` and the shared loading and planning interfaces. See [Robot configuration](references/api.md#robot-configuration). Freeze native models, configuration, and weights with `assets_prepare(resourceFile,dependencyFiles)` and pass report references to the build. Develop behavior against the frozen SDK's actual structure, drives, and readers. Loading a model does not validate a task. Teleportation and object attachment do not constitute robot actions. For liquids and material conversion, consult [Raw measurements and liquids](references/api.md#raw-measurements-liquids-and-generated-calculations) and [Native material support](references/api.md#project-and-scene-tree) when applicable. Report unsupported readers or formats.
- For custom non-robot shapes, implement `build_asset(materials)` in project Python and call `assets_prepare(sourceFile,expectedSourceHash,materialIds)`. At first preparation, supply a descriptive searchable `name`. Explicitly prepare and freeze material inputs. The isolated executor can read only the frozen source and declared materials and has no network access. Use the actual dimensions and coordinates from the report. Inspect visual quality and identify procedural assets as such. See the [asset interface](references/api.md#assets-and-materials).
- Preserve original MDL materials through the native preparation, freeze, and official dependency checks. Declare `mdlSearchRoots` only for absolute module imports that require them. Bare SDK material references do not require an invented root. Declare modules, textures, and tiles in full. If web GLB cannot represent a material, inspect RTX images of the same revision. See [supported material features](references/api.md#project-and-scene-tree) for limits such as connected input graphs. Frozen files, source revalidation, and unknown internal mappings do not establish final appearance.
- Use the native file tools to write `scene.py/tasks.py/rubrics.py`, any requested behavior, and necessary helpers. Respect node boundaries, uses, and dimensions. For robot data also account for the robot's workspace. Build with the native SDK through `world.stage` and bind semantic entities using `world.bind`. Production execution reloads the frozen stage. When delivering behavior, generate its stages, goals, constraints, and recovery. Reuse suitable planners or policies and map them through the frozen I/O contract into named `env.step` commands. Use real feedback to develop an independently rerunnable closed-loop expert. Its production rerun must not rely on coordinates or actions supplied by the author's session. Distinguish planned motion from actual arrival, grasp, release, and task completion. Generate scoring for completion, failure, order, and termination from declared real measurements. Preserve all original requirements and thresholds.
- Reuse the planner with the same model and current world observation. Screen multiple numerical candidates that satisfy the original constraints before execution. Update or replan when joints, grasp relationships, or the collision world change. On numerical failure, try another legal candidate within the current behavior without replaying an already executed physics prefix. Executed state is not a rollback snapshot. See [Trajectory execution](references/api.md#motion-planning-and-policy-reuse) for general tracking. Generate task phases, goals, contact decisions, and recovery. Record the model, coordinates, control, contact conditions, and verification scope of reused experience. Recheck when conditions change.
- After editing environment sources, obtain the current digest with `project_inspect`. Freeze the actual closure with `scene_build(expectedSourceHash, environmentSourceRefs=[...], resourceRefs=[...], requestId)`. With `baseRevision`, `task_check` reports a whole-World diff. It does not calculate impact closure, incremental builds, or sufficient retest scope. Preserve unaffected node identities and requirements and choose verification from the actual report.
- Inspect actual `scene_observe` images of the whole scene and necessary details. Check orientation, proportions, material mapping, texture scale, direction, seams, and intended use. If web preview is unavailable, continue with native images and report the display gap. Confirm required visible dynamic effects in actual execution footage. Physical values or a video file's existence cannot establish visibility. Disclose obscured or unexamined requirements. Choose camera views and duration for the intended recording or policy observation. See [Recording cameras and policy pixels](references/api.md#recording-cameras-policy-pixels-and-semantics). Use bindings, scoring source, and verification episodes from `task_check` to diagnose, edit, rebuild, and retest.
- Each proposed task needs nonempty `evaluation.cases` that can discriminate outcomes under the request and its risks. Choose case counts and normal/failure types for the task. Derive expected outcomes independently of the scoring under test and have the independent reviewer verify them. Exceptions and missing records cannot stand in for ordinary failure. In scene-only mode, pass the current case's `policyRef/digest`, `controller.type=policy`, and `purpose=verification` to `robot_run`, and reference actual episodes through `task_check(episodeIds=...)`. See [Tasks, control, and observation](references/api.md#tasks-control-and-observation) and [Generated scoring](references/api.md#generated-scoring-and-the-three-products) for identity, order, completion, and counterexamples with identical readings. Distinguish logic tests from actual physics checks. Studio supplies no fixed cases by task type.
- When `demonstrations` are requested, specify the task and revision in `robot_run`. Inspect actual scores, actions, keyframes, and demonstration eligibility for each task. The robot must control the execution. Placing objects at goals, static loading, or probing a joint cannot produce a demonstration. Report unavailable grasping or articulation. Do not substitute pushing. For a batch, reuse the frozen expert and required views. Use only seeds permitted by resetSpec. Repeating one seed does not produce layout diversity. Do not call an LLM every control cycle.

Schedule tools by actual dependency. The user does not have to click Build or Run. Give brief progress reports in plain Chinese, citing actual results.

## Scene checks and independent review

Check the following five aspects early and again on the frozen scene and observations. Correct problems and verify the affected scope. Reuse evidence from the same revision. The independent reviewer covers all five aspects, including backgrounds and areas outside the named operation. See [Independent internal review](references/api.md#independent-internal-review) for measurement and evidence limits.

| Aspect | What to verify |
| --- | --- |
| Request match | Objects, properties, functional areas, and initial states match the request. The initial state leaves the intended task for the robot to complete. |
| Task suitability | Destinations, container openings and interiors, moving-part sweeps, working positions, and required routes are usable. Residential rooms need plausible entrances, circulation, and connections between functional areas. Respect tabletop, intentionally closed, and cropped settings. Evaluate working areas as a whole rather than demanding a floor stance for each built-in or suspended component. Scene-only delivery does not require a particular robot to succeed. |
| Geometry | Check scale, boundaries, real support, mounting, and improper intersections throughout the scene, including background furniture. Declared relationships, overlapping bounds, and an object staying still do not settle these questions. Recognize normal assembly. |
| Physics | Check actual collisions, task-relevant articulation, constraints, and state. Retain plausible fixtures and mounts. Check whether proxies block cavities or moving parts. An all-static scene, lack of movement, or a single technical step does not establish usability. |
| Visual quality | Inspect shape, metric material and texture scale, layout, style, lighting, ordinary details, and operation visibility. Examine visible surfaces, edges, and installation finishes. Inspect the full tabletop and close-ups, or the whole room and operation area. In a multi-room scene, look into each room from its entrance or an equivalent whole-room view. Inspect connecting spaces. Judge large empty floors or walls against the room's use and check that furnishings preserve travel and manipulation space. Respect the requested footprint. |

Task scores and format-consumer passes do not establish scene quality. Keep background furniture quality out of task-specific scoring formulas. Check layout, support, activity space, and visibility early enough to catch global issues. Reuse current-revision evidence without a fixed sequence or repeated rendering. In the existing review notes, explain the evidence, necessary areas left unchecked, and why any aspect is inapplicable. The author corrects departures from the request or default quality standard and returns the current revision for review. Known defects or gaps that prevent a necessary judgment preclude a pass. These five aspects guide authoring and internal review. They introduce no new host score, receipt fields, or second review layer.

## Long-running jobs and completion

Use stable `requestId` values for writes. If connectivity is uncertain, check the original job. Retry with its existing ID and use a new ID only for a deliberate new attempt. Long operations return a `jobId`. Call `job(action="wait", waitMs<=30000)`. Pending is normal. A `job.completed` event reports computation ending, and task success may still be false.

Work on independent nodes or continue waiting in the same turn. If a turn must end with work in flight, identify the actual job. The host resumes the same session when it reaches a terminal state. Avoid duplicate submissions and new projects. The web interface handles native approvals and necessary user input. Preserve the objective and generated results.

Diagnose and repair scene, behavior, scoring, and configuration issues within the requested scope. Low scores, policy failures, cross-run physics variation, consumer failures, transient source reads, and a final-stage label alone do not establish a system fault. Inspect stage, timing breakdown, and timeout first. For a corrected or newly evidenced attempt, adjust `workerTimeoutSeconds` to the workload. Preserve failed attempts and candidates, required data, and original requirements. Wait normally for pending jobs and reconcile active or unconfirmed native subtasks. See [Waiting for system support](references/api.md#waiting-for-system-support) for compatibility and diagnostic boundaries.

Use `generation_wait_system` only for a real blocker beyond the project and public interfaces. Submit its cause and actual evidence and end the turn after the wait receipt. System development handles it. Waiting preserves accepted jobs and passed products. Supplemental messages are saved. After repair, explicitly resume the original generation with its requirements, session, and failure history. Do not force continuation with a new project, duplicate failing request, or kernel changes.

Before requesting delivery, export and read back the requested products. A standalone environment needs actual scoring cases and interface checks. Verification episodes are distinct from expert demonstrations. Convene the native direct subagent `scene_quality_review` for independent review. The reviewer does not author or edit products or delegate further. It checks the complete request, current frozen scene, scoring and cases, actual images, and proposed executions. For robot work, confirm the real model and original mechanism. Select views and times according to the task risk. Reuse evidence for the same revision. Report unmet or unverifiable requirements. Make corrections, submit the current revision for re-review, and obtain the reviewer's final [receipt](references/api.md#independent-internal-review). System developers do not review or repair individual products in the generator's place.

Before `project_deliver`, check the complete original request, current scope, and [product requirements](references/api.md#generated-scoring-and-the-three-products). Construction history must be recoverable and linked to consequences. Recorded observations and actions must match the frozen behavior's actual execution. Compatible external policies must be able to run independently with the environment and generated scoring. For `deliveryContract='producer-exports-v1'`, author, run, and repair the exports and package entry points in `delivery/` using the [delivery guide](references/delivery.md). Deliver only the requested ATIF and training JSONL, same-source LeRobot and HDF5, or independently loadable environment directory. Include matching entry points in the manifest. The system does not write format converters. Changing an export does not require rebuilding the scene or rerunning selected episodes. Keep the original contracts of older jobs. Failed episodes and continuous outcomes do not establish successful demonstrations. If successful execution is requested, obtain actual evidence. The reviewer selects records from the same revision by [intended use](references/api.md#independent-internal-review). Interface probes do not count as demonstrations or closed-loop success rates. Check requested replay accuracy, repeated success, and generalization under their predefined conditions. Low scores from external policies do not revoke the environment receipt.

Pass the current requirement binding and the native final source `review={threadId,turnId,itemId}` to the [delivery interface](references/api.md#independent-internal-review). An author assertion or an old revision's pass is invalid. For multiple layouts, bind `environmentRefs` and the actual `revision/taskId/use` of each execution. Review and consume separately by revision and task. Scene-only `coverage.episodes` may be empty. Demonstrations must cover the locked collection tasks. Changes to selected executions or uses require supplemental review and a new requestId. Announce completion only on host `accepted`. For `incomplete`, follow up on the outstanding items. Record failure, interruption, and unknown context faithfully. If capabilities or budget are exhausted or the user cancels, identify completed scope, remaining work, and the specific cause.
